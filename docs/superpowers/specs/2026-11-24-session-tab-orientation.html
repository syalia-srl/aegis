Design specification · v0.2 · 2026-11-24 · Issue #1146

Configurable session tabs with a collapsible left list

Status: draft for independent review and product approval. The collapsible left list is agreed. The detailed defaults below are proposals. This document authorizes no implementation, planning, release or merge.

OutcomeBehaviorContractsAcceptanceEvidenceDecisions

Problem and outcome

The full client puts open sessions in a horizontal scrolling strip. With many open sessions, only part of that strip is visible. Offer a vertical list on the left so a person can scan more session names while keeping the conversation and session details available. The person can collapse that list to recover its width and reopen it from a persistent control.

This is an alternative arrangement of the existing session navigation, not another session registry or a replacement for Fleet. The user of the feature is the person switching among open sessions, including groups and sessions from linked servers.

Scope and boundaries

Apply to the standalone full client (layout: full, page: true) wherever its normal global header is present. The preference remains consistent when navigating between session, group, Fleet, Settings and other full-client views. The new left list is global session navigation; the right panel continues to describe the selected session.

Embedded full mounts (page: false), embedded chat and tabs layouts, and secondary canvas windows that intentionally omit the header retain their present contracts. No new mount option or host API is introduced. A stored standalone preference must not alter an embedded mount, even on the same origin.

Non-goals: automatic orientation, a resizable left list, an icon-only collapsed rail, new grouping or sorting semantics, cross-device preference synchronization, a redesign of Fleet, changing canvas pane tabs, or changing session ownership and lifecycle. Scope expansion requires revisiting this design.

Observable behavior

Orientation

Add a browser preference named Session tabs in Settings → This browser, with Horizontal and Vertical choices. Horizontal is the default when there is no valid stored preference. Changing the choice takes effect immediately. Opening or closing a session never changes the chosen orientation.

Horizontal retains the existing strip and overflow switcher. Vertical replaces that strip with a 232 CSS-pixel list at the left; it does not show a duplicate strip above it. The global header keeps Fleet, New, connection status and its existing view/action controls. The vertical list scrolls independently and retains the existing themed session rows, titles, group styling and attention glyphs. Long labels truncate within the list, with the existing full accessible label and hover/touch details still available.

Collapse and reopen

In desktop vertical mode, a Sessions control remains in the top-left header whether the list is open or collapsed. It uses the existing panel glyph, oriented toward the left. When expanded its action is Collapse sessions; when collapsed its action is Show sessions. Collapsing removes the entire 232 px column and allows the current view to use that width. It neither switches to horizontal mode nor leaves an icon rail.

The left list and the right details panel have independent state. Toggling either must not change the other. A newly selected vertical mode starts expanded unless a previously saved vertical collapse preference exists. Temporarily choosing horizontal, visiting another view or narrowing the window does not erase that preference. Reopening exposes the selected session without changing selection or group folds; use the existing folded-group rule that keeps the focused member visible.

The all-sessions switcher remains accessible from the header and its existing keyboard shortcut while the list is collapsed. New session and notification controls remain reachable. Incoming attention updates do not expand the list automatically; existing notification and switcher behavior remains in effect.

Narrow windows

At viewport widths of 760 CSS px or less, use the existing horizontal phone strip regardless of the saved desktop orientation. Hide the new collapse control at that width. Do not write Horizontal into the stored desktop preference. At 761 px and above, restore the selected orientation and its saved collapse state. This follows the current standalone client's viewport breakpoint; it introduces no new embedded-container measurement contract.

For example, Vertical + collapsed on a wide window becomes the existing horizontal strip on a phone; widening the window restores Vertical + collapsed. The existing right-panel drawer remains independent. A left phone drawer is an alternative, not part of this proposed first version.

State-preserving examples

  • With session B selected, a half-written message and the right panel open, collapse the left list. Session B, the draft and the open right panel remain; the conversation becomes wider.
  • Switch Horizontal → Vertical with 24 sessions, two folded groups and a popped-out member. Preserve the same logical order, membership and folds; only placement changes.
  • A linked-server session with a long title retains its server label and actions. Orientation must not change the server to which an action is sent.

Semantic contracts and invariants

Sessions
The server owns the set of open sessions. Closing a session has the same existing server-wide effect. Hiding the navigation does not close, quiet or unsubscribe any session.
Ordering
The existing browser-local logical order is shared by both orientations. No parallel vertical order is introduced. Group heads, folded members, quiet-member counts, detached members and browser/terminal tabs keep their current meanings.
Selection
The active route, selected session and focused group remain unchanged by orientation and collapse operations. Preserve drafts, transcript reading position, active uploads, running artifact/browser frames and canvas placement. Apply layout changes without restarting the session or remounting its active content.
Persistence
Store orientation and vertical collapse state as separate browser-local preferences, scoped to the current origin, alongside the existing browser settings. Read them before drawing the chosen layout on reload. Unknown values default to Horizontal and expanded. The fallback guarantee covers reads and writes of these two new preferences only. If their reads fail, start with Horizontal and expanded; if their writes fail, apply orientation and left-list folding in memory for the current page lifetime. Such failures must not interrupt these controls or reset unrelated navigation state. Existing tab-order and group-fold storage operations remain unchanged. This feature does not guarantee startup or navigation when all browser storage access is disabled: the current header has independent direct storage accesses outside this scope. No server write or session record is involved.
Other windows
New or reloaded standalone windows read the saved preference. Immediate synchronization into already open windows is not required. Each open window may retain its current layout until changed locally or reloaded.
Dragging
Preserve existing reorder, group join/leave, group-block moves and invalid-drop rules. Horizontal uses left/right placement; vertical uses above/below placement, including group gaps, drop indicators and scrolling during a drag. Orientation does not reinterpret a group operation as merely moving a row. A layout change during a drag cancels the unfinished drag without committing a move.
Theme
Use the current product CSS, font assets, sprite and translated labels. Do not add a separate mockup-inspired theme or replace glyphs with emoji. Product controls and states must work in every shipped theme.

Keyboard, touch and focus

The collapse control is a native button, reachable by keyboard, with an accessible action name, aria-expanded and aria-controls. Enter and Space operate it. Focus stays on that button after a toggle while it is visible. Hidden session rows must not remain in the tab order. If a change hides the focused navigation row on a wide vertical layout, move focus to Sessions. When narrowing or zooming across 760 px hides a focused Sessions control, move focus to the existing visible phone menu button (the header burger), without opening its menu. On widening, if that focused phone button becomes hidden, move focus to Sessions in Vertical or Fleet in Horizontal. Use the same visible destination for any focused navigation row hidden by the corresponding transition. Do not move focus if the focused control or content remains visible. Existing session switcher and keyboard move actions keep their semantics. Reopening brings the active row into view without stealing focus from the button.

Keep the existing minimum touch targets and reduced-motion behavior. Do not require hover for reopening, choosing sessions or accessing actions. Width changes must not create horizontal document overflow or cover the composer at desktop transition widths or at 390 px.

Decisions, alternatives and approval

Agreed
A left-oriented session list must be collapsible and reopenable. The visual comparison must retain Aegis's actual styling. These requirements are settled; implementation is not authorized.
Proposed
Manual orientation; Horizontal as default; 232 px fixed list; a persistent Sessions button with no collapsed icon rail; browser-local preferences; current horizontal navigation at ≤760 px; standalone full client only. These choices remain pending approval of this version.
Deferred
Automatic switching would need stable thresholds and protection against repeated reflow. A resizable list adds another preference and drag interaction. A left phone drawer shows more names but adds an opening step to switching. Embedded support changes host layout contracts. Each is a separate future decision.
Priority
Implementation scheduling remains pending under vision #715. Specification approval is neither a milestone exception nor authorization to plan, implement or merge.

Approval should identify the document version and accept or amend its proposed defaults. A requested change to automatic behavior, embedded hosts, persistence scope or narrow-window navigation requires revising the affected criteria and obtaining review of those changes.

Independent review

A fresh reviewer assessed v0.1 against the explicit source manifest and requested two important corrections. Both are addressed in v0.2; independent confirmation is pending. The review is static and establishes no product acceptance criterion as passing.

  • GF-01 — corrected: the persistence guarantee and VT-03 now cover failures of the two new preference operations only. Existing tab-order and group-fold storage remain outside the fallback scope; in-memory left-list folding is explicitly required.
  • GF-02 — corrected: the accessibility contract and VT-04 now name visible focus destinations for narrow/wide transitions, including browser zoom, and prohibit opening a menu as a side effect.

No findings were rejected. Product choices listed above remain pending approval.
