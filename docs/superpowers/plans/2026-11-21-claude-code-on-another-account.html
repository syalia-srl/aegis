Claude Code on another account: the plan

docs/superpowers/plans/2026-11-21-claude-code-on-another-account.html·spec: docs/superpowers/specs/2026-11-21-claude-code-on-another-account-design.html·against main a2c8d5e

Two PRs. A makes the pool a property of the session, so a Claude Code session that talks to OpenCode Go is measured, guarded and billed as Go's. B gives a claude-code agent a connection of its own — endpoint, key, pool, restricted environment — so that session is started without the Claude sign-in token. One commit per task where it can be; B1 and B2 share a PR, because a record that names a pool while the process still holds Claude's environment would make the card lie.

How this runs

  • Issue, then worktree, then PR. One issue per PR, filed before the branch from origin/main. Neither issue is filed, and nothing is branched, until the person approves this plan.
  • A first; B branches from origin/main after A merges, never from A's branch (a stacked PR closes itself when its base merges).
  • The slice is the unit of work, one queue worker per slice on general, each after the one before has come back: the slices touch the same files and would collide in one worktree. A1 before A2, A3 and A4; B1, then B2, then B3 and B4 in that order.
  • A worker runs only the tests its tasks name in the verify blocks, plus make lint-docs when it touched a help page. The full suite is CI's job: merge main, open the PR, let CI run the suite and the bench.
  • A review agent only where the work can hide something: A2 (recorded state and keyed cooling) and B2 (a child's environment, a credential). A1, A3, A4, B1, B3 and B4 have tests that pin their behaviour.
  • No merge without the person's yes. Each PR ends green, with its screenshots in the body, and stops there.
  • Isolation is the agent's switch, not a rule. The person answered: a connection session is not forced into isolation; aegis doctor warns when a connection agent leaves it off, and B2 keeps the decided cut of the credentials link for the sessions that do run isolated.

Where this plan departs from the spec

Seeded while writing the plan; it grows with each worker's report before the PR.

  • The card's pool is resolved, not recorded. card() carries pool_of(spec) for every session, not spec.pool. A card that carried only a recorded pool would leave every existing session without one, and the sidebar would draw no gauge at all until B1 set a pool. The record's field is what pool_of prefers, so the two never disagree.
  • cooling_owner is a function, and pick takes the pool as a callable. A cascade with no connection can change pool from one model to the next (OpenCode models under different prefixes), so the pool of the candidate model is asked per model, like its gate.
  • Cooling.wire has no caller on main a2c8d5e. Found while writing this plan; it answers open question 6 of the spec. The wire still names the pool for a pool fall so a later reader is not misled.
  • App.gate takes the pool as its third argument. It still answers open: it is the host policy's gate, whose lines left with multi-user mode (#958); only the argument stops naming a harness.
  • There is no sidebar gauge test to change. providerFor has no test on main, so A3 adds tests/test_pool_browser.py rather than editing one.
  • R1-01 is answered: no forced isolation. The person keeps isolated as the agent's own switch, with a doctor warning for a connection agent that leaves it off; B2 still removes the credentials link for an isolated connection session. Isolation would not close the reach anyway — HOME is unchanged, so ~/.claude/.credentials.json stays readable — and the plan does not pretend otherwise.
  • Two gaps a builder's read of the plan found (the spec's author, on its own text): the run-time check of api_key_file — missing, not 0600, another owner — was only in doctor's task, and is now step 3 of task 15, where the key is read; and B1's task asserts that a restart keeps the record's connection after the agent is edited.
  • pool_of takes a Pooled protocol, not SpawnSpec. A1's first commit added the resolver before a spec had a pool, and quota_gate must not import session; SpawnSpec satisfies the protocol structurally.
  • Test stubs gained pool=None. tests/test_notices.py's SimpleNamespace spec did; any other stub that reaches notices.pending, quota_guard or Schedules._line without one fails with AttributeError, which CI will name.
  • A1's schedules test sets a.spec by hand (dataclasses.replace), because nothing writes a pool into a spec until B1; that line goes when B1 lands.
  • There is no quota help page. The spec said "the quota and usage pages"; src/aegis/help/ has usage.md and sign-in.md, so A and B document pool and unpriced turns on usage.md.
  • A2's fall key keeps a pool in its own space. _pool_key(owner, model, pool): a named pool keys (pool, "pool", pool); an endpoint keys itself, so two unmetered gateways never share; a harness that derives a pool keys the pool alone, so all Claude Code sessions share claude; a harness with no derived pool keeps its own name in front (("opencode", "pool", "claude") for a claude/x model); and pool: none without an endpoint cools the model alone. A pool fall never cools Claude by accident.
  • App._cooling_owner(spec) passes no endpoint yet. It is cooling_owner(spec.harness, None) until SpawnSpec.connection exists; B1 replaces its body with the connection's base_url.
  • The cooling wire changed shape. A pool fall emits {"pool", "until"}; a model fall emits {"harness"|"endpoint", "model", "until"}. Nothing reads it on main, and a pool: none pool fall shows the endpoint URL in pool — accepted, since the field is for a person reading a future client.
  • _is_endpoint reads the text, not a type. A base_url without a scheme would be treated as a harness; B1 refuses anything but an http or https URL, so it cannot reach here.
  • A recorded pool outranks apiKeySource in billing. B1 refuses pool: claude on a connection and records no pool on an agent without one, so no turn that bills today changes.
  • The card is Session.wire(), not Session.card(). A3 put pool where the sessions channel builds its message; the spec's word "card" names the same thing.
  • A linked server on an older aegis draws no gauge. Its cards carry no pool, and providerFor matches on the pool alone now: that is the spec's rule, and the PR body says so.
  • The browser test needs the Playwright build the worktree pins. This server had an older one; A3 proved the test with it through a temporary plugin outside the repo, and installed nothing. CI has the pinned build.
